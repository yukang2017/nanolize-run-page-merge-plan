先说一件容易误会的事

“从 main 开新分支再合入分支”和“从分支开新分支再合入 main”，合出来的文件内容是完全一样的。两种做法我都实际做了一遍，得到的是同一个树对象。方向决定的是历史的形状和 PR 的读法：从 main 开，main 是第一父提交，main 的历史原样在前，PR 相对 main 的差异就是加进来的东西，审的人看到的每一行改动都是“相对已验证的 main 变了什么”。这正是你要的，所以方案按这个方向做。但真正保证 main 的内容不受影响的不是方向，而是下面这两项核对。

Git 报出来的冲突怎么解

5 个文件，10 处。下面每一处都在本地的试合并里按这里写的办法解过，解法写成了一个脚本，重做一遍只要几秒。

C1

run-dashboard.js：交付是否成功的判断条件

2 处要小心
两边做了什么
第 06 阶段里有一段代码，列出“交付成功”要满足的条件：行为检查通过、原版基线就绪、安装通过、性能保持等等。
  • 分支把这段代码搬进了一个新函数 outcomeCriteria，因为页头的状态标记和结束时的说明现在也要用同一份条件；原来的位置只剩三行。
  • main 在原来的位置改了一行：项目没有声明任何性能时（not_declared），不把“性能保持”列为条件。没有要保持的东西，既不算通过也不算缺口。
为什么要小心
Git 在原来的位置报冲突，两边看上去是“一大段旧代码”对“三行新代码”，很容易直接取分支那一边。那样合出来的文件没有任何冲突标记，却把 main 的规则丢了：分支的新函数里还是老写法 if (speed) …。后果是 performance=on 而项目没有声明性能的作业，页面会在交付结论下面列出一条不成立的“性能保持”，结束时的说明也把它算成没有守住的条件，而实际上什么都没有测、也没有什么要守。
解法
原位置取分支的三行；然后在 outcomeCriteria 里把 main 的规则写进去： 
// 分支的写法
if (speed) criteria.push({label: T("Performance preserved"), ok: speed.status === "passed", why: ""});

// 合并后
if (speed && speed.status !== "not_declared")
  criteria.push({label: T("Performance preserved"), ok: speed.status === "passed", why: ""});
第二处冲突是文件末尾的导出列表，两边各加了名字，取并集（main 的 CLAIM_REASONS、claimLines，分支的 outcomeCriteria、endNote、runSpan、stepLimit、span）。
怎么知道解对了
我特意按错误的办法解了一遍（直接取分支那一边），main 自带的测试“a project that declares no performance is told so in every place, never as a gap and never as preserved”失败，395 项里错 1 项。按上面的办法解，395 项全过。调查还确认了这一处改动同时管住了页头的状态、结束说明和页面第一行下面的说明，因为它们都读这个函数。

4 处两边都留
两边做了什么
  • main 给 _in_copies（在树的私有副本里同时跑多条检查）加了三个参数：retired（被检查弄脏、不能再用的副本）、places（每条检查在哪个副本里跑的）、length（让副本的路径和候选树一样长）；还加了两个新函数 _copy_place、path_length，并让设计出的测试文件的试跑也走副本。
  • 分支加了一个上下文变量 PROGRESS 和一个参数 ended，让比较步骤能报告“多少条检查已经有结果、现在能同时跑几条”，运行页据此画进度条。
解法
四处都是在同一个位置各加各的：
  1. 模块里的同一个空位：main 的两个函数在前，分支的 PROGRESS 在后。
  2. 函数签名：参数取并集，…, retired=None, places=None, length=None, ended=None。
  3. 文档字符串：两边各自的段落都留。
  4. _run_checks_here 开头：留分支的计数代码。它下面跟着的两行注释是分叉点的旧注释，main 已经把那一段改写成了新的分支，这两行不留。
合起来对不对
对。进度只在比较步骤（compare_behavior）里才打开，而比较步骤那一批检查不走 main 新加的任何一条路径（不试副本、不换种子、不问另一个路径），所以 main 的新调用都不会经过分支的计数；计数用的是这一批检查名字的集合，不会超过总数，也不会重复算。分支在函数体里加的那几行（一条检查在副本里跑完后报一声）被 Git 自动合进了 main 改过的函数体，位置是对的，在“副本是否退役”的处理之前。查轨迹工具的那份调查自己独立解了一遍这个文件，结果和试合并里的逐字节相同。

2 处重新生成
为什么会冲突
这个页面把运行页的脚本整份内嵌在自己里面。两边都改了 run-dashboard.js，各自刷新过这个页面，所以冲突的位置和内容就是 C1 的翻版。
解法

画面数据不变，只换内嵌的脚本和样式。另外两个演示页没有冲突，但同样过期，要一起重新生成，见 M2。

M1

公开级别的轨迹会带出性能声明的出处、原句和命令

轨迹记录器已定：不带
现象
nanolize trajectory record --detail public 的承诺写在分支的 docs/trajectory.md 里：只留编号、枚举、计数和时间，没有文件名，没有参数，没有所有者的回答。但记录器把作业的 result 整份照抄（trajectory.py 里的 "result": public.get("result")）。在分叉点，这份结果里没有文字；PR #59 把每条性能声明的出处文件、行号、引用的原句（最长 500 个字符）、“测的是什么”的句子、项目自己的运行命令，以及测量用的 GPU 型号，都放进了 result.performance。
核实
用合并后的记录器读 PR #59 自己那次 detectron2 端到端运行留下的记录，公开级别的结果里有 5 条声明，条条带出处、句子和命令，还有 GPU 型号。轨迹页面不画这些内容，但页面是一个把数据整份内嵌的单文件，JSON 文件里也有。其余路径都查过，只有这一条会带出文字：别的字段记录器都是按名字挑着留的。
影响
公开级别就是为了给别人看而设的。对一个私有项目，文档里的句子、文件名和命令会跟着轨迹文件出去，而文档明说不会。
改法
公开级别时，把结果里的声明缩成编号、能力、设备、状态、是否比较过、用了几块 GPU、原因和结论，去掉 GPU 型号。main 已经有做这件事的函数（performance_evidence.claim_outcomes），所以只是在记录器里加一个十行左右的小函数；测试用的夹具里加一条带出处的声明，断言公开文档里没有那些文字；docs/trajectory.md 补一句“所有者级别带声明引用的原句”。
没有选的方向
反过来定也可以：公开轨迹跟着作业的公开结果走，声明照带，然后把文档改成这么说（PR #59 对公开的选择页就是这么定的）。但记录器自己对能力名称和文件名的规则是“公开级别不留”，两者放在一起会自相矛盾。你已经定下按“改法”做。

固定流程的基准记录要重录

tests/fixed_parity_golden.jsonCI 看不到
现象
test_fixed_parity 把固定流程的作业产出的所有东西和一份录好的记录逐项比较，其中包括“运行页显示这个作业的什么”。这份记录只在录制它的环境里可比，CI 上会跳过，所以 PR 的 CI 全绿也发现不了它过期。合并后的代码上，9 个场景的测试在 run_page 这一项上失败，连带 42 个中断续跑的测试失败。

S1

提交之前看不到这次要测哪几条性能声明

选择页四处里最要紧
现象
PR #59 的设计是：选择页在提交之前列出项目的性能声明，连同“只有落在你选中的能力上的声明才会被测”这句提醒；它们放在页面的“规划说明”里。分支让嵌在运行页第 02 阶段里的选择页默认只显示能力图，其余内容收在“Show details”按钮后面，“规划说明”也在其中（viewer.css 里对 #limitations-panel 的隐藏规则）。按钮上会提示后面有几条“注意”，但只数另外两块内容，不数规划说明。
后果
有人值守、开了性能验收的运行里，所有者在运行页上看到的是能力图、预设和提交按钮，看不到这次要测哪 5 条、哪些因为没选中而不会测；项目没有声明性能时，“这次什么都不会测”那句话也看不到。按钮上没有任何提示。单独打开的选择页不受影响。两边的 skill 文字也各说各的：一句说选择页列出声明，一句说它只显示能力图。
改法（两种，已定第一种）
  1. 按钮上说出来。规划说明里有性能声明时，按钮写成“Show details · 5 performance claims”，并和现在有“注意”时一样高亮。改动最小，保持分支“只显示图”的设计。
  2. 开了性能验收时不折叠规划说明。声明列表直接显示在图的下面。更稳妥，代价是这种情况下页面不再只有一张图。
同时把 skill 里的那句话对上：告诉用户声明在“Show details”后面。
S2

“项目没有声明性能”那句话被折叠起来了

运行页 第 05、06 阶段
现象
PR #59 给“开了性能验收、但项目没有声明任何性能”的作业只留了一句话，放在第 05 阶段的关卡和第 06 阶段的条目里，状态是“跳过”，代码注释里写着“这两处说明原因，仅此而已”。分支把所有“完成”和“跳过”的条目折叠成一行（“1 done · 2 skipped”），这句话正好在里面。
后果
结论的判断条件里没有性能（这是对的），页头和结束说明也不提。于是默认状态下，整个页面没有一处告诉所有者：你打开的性能验收为什么什么都没做。

给这两个条目加一个“不折叠”的标记，折叠时跳过带标记的条目。只动这两处，其他性能条目照旧。
S3

环境准备失败的交付，被说成“没有任何失败”

运行页 结束说明
现象
分支加了一句结束说明：如果一次“有缺口”的交付，缺口只是“没人配置的检查”（比如没配安装检查），就说“Nothing failed. Not checked, because nothing is configured for it …”，并把状态标记画淡。它判断的依据是页面自己的那份条件列表，不读交付记录里实际列出的缺口。PR #59 新加了一种缺口：所有者配了环境准备步骤，而交付的候选版本上准备失败（candidate_preparation_not_passed）。页面的条件列表里没有它。
后果
准备步骤失败、又没配安装检查的作业，页面会说“没有任何失败，只是安装检查没配置”，状态画淡，第 06 阶段也没有任何条目提到准备失败。PR #59 加这种缺口，本意就是让这样的交付把它说出来。这个弱点是分支自己的（原有的几种没有对应条件的缺口也一样），PR #59 只是又添了一种，而且是检查全过时也会出现的一种。
改法
交付结果里有缺口列表时（result.acceptance.gaps），以它为准：只有全部缺口都是“未配置”才说“没有任何失败”，否则在“没有守住的”那句里把其余缺口说出来。再给新缺口补上页面用的说法。
S4

重做的测试设计，会话数被算成两倍

轨迹记录器
现象
PR #59 让被打断的测试设计在重做时接手已经做完的会话：为每个接手的会话写一份记录，里面时间和用量都是 0，并标着 taken_over。作业自己数会话时不算这些。轨迹记录器把作业目录下每一份这样的记录都算作一次模型会话。
后果
token 和时间是对的（接手的那份是 0），但会话数翻倍：PR #59 为之设计的那个场景里（60 个设计会话和 30 个评审会话被接手），轨迹会说 180 次会话，实际跑了 90 次。而且这些 0 用量的记录被当成“没有成本数据的会话”，页面会把一份完整的成本说成“下限”。
改法
记录器里加一行：带 taken_over 的记录不算会话，另外计数（“读到 N 份，其中 M 份是接手的”）。夹具里加一份这样的记录。
把握
依据是两边的代码和一份手工做的记录；PR #59 的端到端运行里没有出现过重做的设计，所以没有真实记录可验。

合并步骤

做法已经定下：从 main 的最新提交开新分支，把分支的改进合进来，再开 PR 合回 main。新分支的起点就是 main 本身；main 是合并提交的第一父提交，它的历史原样在前；分支的 6 个提交原样保留在第二父提交那一侧；PR 相对 main 的差异正好就是加进来的东西。远端的 main 在 PR 合入之前不会有任何变化。

  1. 从 main 的最新提交开一条新分支

    不在 claude/run-page-improvements 上开，也不往它上面提交；它原样留着。

    git fetch origin
git switch -c claude/run-page-on-main origin/main
  2. 把分支合进来，先不提交 
    git merge --no-ff --no-commit origin/claude/run-page-improvements

    Git 会报 5 个文件冲突，其余 18 个两边都改过的文件自动合并。这个方向上 main 是“我方”（ours），分支是“对方”（theirs）。

  3. 按 C1 到 C4 解冲突，原则是 main 的内容一行不丢

    每一处都是在 main 的代码上把分支的改动加进去；C1 里 main 的规则保留，只是随分支的结构换了位置。生成的演示页取分支的版本。试合并里这一步已经写成脚本，每一处替换都要求“恰好匹配一次”，对不上就停，不会悄悄解错。

    git checkout --theirs docs/run-page-demo.html
  4. 重新生成三个演示页（M2） 
    python scripts/run_page_demo.py refresh
python scripts/run_page_cases.py build
python scripts/trajectory_demo.py refresh
  5. 核对 main 的内容，跑快的检查，然后提交合并

    先重做那两项逐文件的核对：PR #59 的改动原样保留，加进来的只有分支的改动。再跑下面这几步，登录机上几十秒就完。合并提交的说明里写清楚：C1 里 main 的规则搬进了哪个函数，三个页面是重新生成的。到这一步，新分支相对 main 的差异是 67 个文件，+22,486 −1,062。

    python scripts/sync_workflow_docs.py --check

node --test tests/*.test.cjs tests/*.test.mjs
git add -A && git commit
  6. 对照测试和修复提交：M1，以及 S1 到 S4

    先加一条对照测试，单独一个提交：同一次比较，开和不开进度报告，检查结果逐项相同（分支对检查执行代码的那一处改动因此有据可查）。然后每个修复一个提交，各带一条“没有这个修复就失败”的测试。提交说明按仓库的习惯写：原来是什么样，现在的规则是什么。这五个修复都在轨迹记录器和页面的脚本里，不碰 PR #59 的后端；其中 S2、S3 会在 PR #59 写的页面脚本里各加一个标记、一个词。

  7. 再重新生成一遍演示页

    S1 到 S3 改了页面的脚本和样式，三个页面又过期了。把第 4 步的三条命令再跑一遍，单独一个提交。

  8. 重录基准记录（M3）

    在计算节点上、和录制 main 那份记录相同的环境里重录，核对差异只有 report 那一个字段，单独一个提交。

  9. 整套测试，推送，开 PR

    整套 Python 测试在计算节点上跑一遍，和 main 的结果对照；推送新分支，开 PR 进 main，等 CI 的 13 项（两个 Python 版本各 6 片，加打包）。

    用合并提交，和 PR #56、#57、#59 一样。合入由你来按。

为什么不用另外两种办法

  • 变基或逐个摘取（把 6 个提交一个个挪到 main 上面）。分支的 6 个提交每一个都改了生成的演示页（其中两个各改了五六千行），3 个改了 run-dashboard.js。逐个挪要在这些提交上反复解同样的冲突，生成页每次都得重新生成，而中间几个提交的页面已经无法忠实重建（第 4 个提交删掉了前面用来录制的脚本和场景）。仓库的 PR 本来就是用合并提交合入的，这样换不来更干净的历史。
  • 压成一个提交。历史最简单，但分支的 6 段提交说明各有二十六到六十二行，逐条写着页面的每个行为和原因，压掉就丢了。如果你更想要单个提交，可以在合入时选“压缩合并”，前面的步骤不变。

如果执行之前分支或 main 又有新提交：从第 1 步重做。解冲突是脚本，重新生成是命令，整个过程几分钟；需要重看的只有新提交碰到的地方。
